# 如何验证数值、状态与跨语言行为

[上一章](development.md)讲怎么把需求变成改动；这一章讲怎么证明改动是对的：预期值从哪里来、什么样的证据才算证据、"实现正确"与"某次运行看起来对"有何区别。质量规范（覆盖率、门禁命令、风险分类）以仓库 [quality_checks_spec.md](https://github.com/jyzhu-pointless/natal-core/blob/main/quality_checks_spec.md) 为准，本章只说方法。

## 预期值的四种来源

| 来源 | 适用场景 | 例子 |
| --- | --- | --- |
| 手算 | 阶段数量、概率、简单位点模型 | 100 个杂合子 × 2 卵 = 200 后代，孟德尔分配 50/100/50 |
| 不变量 | 守恒、对称、边界 | 迁移前后堆叠总量不变；`g(1) = 1`；行和恒为 1 |
| 解析关系 | 参数与结果有闭式关系 | `s* = K / (产卵量 × 平均年龄-0 生存率)` |
| 既有测试 | 已有合同 | 投影、合同映射、恢复路径 |

本指南正文里的每个数字都注明了来源类型；不确定来源时，先退回不变量或手算，而不是"跑一遍看看"。

## 什么不算证据

| 观察 | 为什么不够 |
| --- | --- |
| 程序跑通、没报错 | 形状相同语义不同时同样跑得通 |
| 总量正确 | 顺序、分组、索引错误都可能保持总量 |
| 一次随机运行接近预期 | 一次实现不是分布；应比较分布或切到确定性模式 |
| 确定性结果与随机结果"大致一样" | 两者是不同声明，需要各自的判据 |
| 测试全绿 | 只覆盖已断言的行为 |

## 五类需要专门核验的行为

1. **数值与阶段**：中间边界（`early`、`late`）与最终状态分别核对；总量相同不代表阶段正确。
2. **状态与所有权**：写入快照无效、会话持有权威、共享数组不可写——这类行为要用"改了它之后有没有生效"来验证，而不是看总数值。
3. **原子失败**：非法候选不产生部分写入；回调失败保留先前提交（见[回调事务](transactions.md)）。
4. **索引一致性**：压缩前后按**类型身份**对照结果，而不是按索引位置。
5. **跨语言位级一致**：同一输入下 Python 侧与原生侧的结果要求逐位相同；涉及累加顺序的改动（例如后代张量）必须保持顺序（见[关键数值算法](algorithms.md)）。

## 统计检查怎么写

当结果本身是随机的，判据要写成统计形式并给出容差：

| 检查 | 写法 |
| --- | --- |
| 期望值 | 大量重复种子的均值落在期望附近，给出容差与依据（例如 60 个种子的成体总量均值 102.0，期望 100.0，容差 5%） |
| 可复现性 | 同种子逐位相同；换种子不同 |
| 抽样类型 | 离散模式数量为整数；连续模式保留小数 |
| 退化分支 | 总量为 0、概率和为 0 时不抽样、不除零 |

不需要为了"看起来严谨"堆很多重复；给出容差依据比增加样本量更重要。

## 怎么读 agent 给出的证据

拿到 agent 的验证结论时，逐项对照：

1. **预期值有没有来源**：是手算、不变量，还是"和上次一样"？
2. **断言的是不是可观察行为**：断言私有字段的重排，还是用户能看到的结果？
3. **有没有可区分场景**：如果正确与错误实现在这组输入下表现相同，这组输入不构成证据。
4. **未验证范围有没有说明**：没有覆盖的模型组合、路径、模式。
5. **命令是否贴出了实际输出**：而不是"应该会通过"。

一句"已验证"不足以交付；需要能复现的命令、数值与失败时的表现。

## 本指南自身的核验方式

这套指南里的数值来自按批次编写的核验脚本（完整初始化、原生运行、断言），每个批次交付时记录：

- 脚本路径与实际运行结果；
- 双语严格构建的结果与警告数；
- 文档检查（标题层级、代码块与图表数量、链接、表格列数、构建页面中的图表）；
- 明确区分"自测"与"独立审查"。

脚本与临时工具可能随系统清理消失，因此结论以仓库内可重复的命令与既有测试为准；本指南不把一次性脚本的成功当作项目全量门禁通过。

## 变更与验证的对应关系

| 变更类型 | 最少需要 |
| --- | --- |
| 文档 | 准确性、双语同步、链接与构建 |
| 局部代码 | 针对性测试 + 交付前完整门禁 |
| 高风险代码（公式、随机分布、状态恢复、共享可变数据、公开 API、跨语言交换） | 独立审查 + 独立运行完整门禁 + 必要的测试补强 |

分类与协作方式以仓库 `AGENTS.md` 为准；本章不另行设定门禁。
